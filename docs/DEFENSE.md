# Подготовка к защите

Документ собран по фактическому коду репозитория (ветка `dev`, 2 октября 2026) и по реальным цифрам из данных. Там, где реализация расходится с планом из `ARCHITECTURE.md`, написано, как сделано на самом деле.

---

## 0. Суть за 30 секунд

**Задача.** Заказчику СПб (АИС ГЗ / Электронный магазин) нужно понять, кого позвать на закупку: кто реально придёт и может выиграть, и кого нового можно привлечь, чтобы было больше конкуренции.

**Что сделали.** Веб-сервис: вводишь категорию ОКПД2, НМЦК, площадку, при желании ИНН заказчика и получаешь:
1. **Ранжированный список поставщиков из истории.** Модель LightGBM (learning-to-rank) обучена на 2 годах закупок. У каждого поставщика есть «подходимость» 0–100, объяснение, почему он в списке (вклад каждого фактора), реквизиты, история участия и графики активности.
2. **Новых поставщиков, которых нет в истории.** Их находим через DaData (ЕГРЮЛ) по ОКВЭД, соответствующему категории, в СПб и ЛО. Роль (производитель / дистрибьютор / поставщик) определяем по ОКВЭД.
3. **Пакетный режим.** Загружаешь CSV с будущими лотами, система считает подбор по каждому лоту и выгружает CSV с топ-10 и причинами.
4. **Шорт-лист** с комментариями.

**Главная цифра.** На закупках IV квартала 2025 года, которые модель не видела, реальный победитель попадает в наш топ-10 в **53,5%** лотов. У бейзлайна «топ по победам» **31,4%**. Медианная позиция победителя **4** (у бейзлайна 14). Потолок из-за отбора кандидатов 71,3%, значит модель берёт примерно 3/4 достижимого.

### 1.3 Ключевой инсайт по данным

**Конкуренция есть только в Электронном магазине.**
- В АИС ГЗ в среднем 1,0 участника, **99,9% лотов с единственным участником**. По сути, в данных видна только заключённая сделка.
- В Электронном магазине в среднем 2,69 участника, с одним участником 41,5% лотов.

Что из этого следует для решения:
- Учимся только на конкурентных лотах (≥2 участников). Только там есть информация, «кто пришёл, а кто нет». На лоте с одним участником учить ранжирование нечему.
- Признак «лот в ЭМ» после этого внутри обучающей выборки почти константа, поэтому модель его не использует (важность 0). Это нормально, не баг.
- Проблема заказчика видна прямо в данных: 71% закупок проходят без конкуренции. Поэтому мы отдельно поднимаем в выдаче **«претендентов»**, которые часто участвуют, но редко выигрывают, и показываем **новых поставщиков**.

## 2. Загрузка и очистка (`parser/`)

Запуск: `python -m parser.load --data-dir <папка с CSV> [--replace | --append] [--dataset имя]`.

Как это работает:
1. **Тип файла определяем по заголовку**, а не по имени файла (`detect_table`). Если файл не подходит ни под один формат, получаем понятную ошибку с ожидаемыми колонками. Файл заявок необязателен: без него это «пакет» будущих лотов.
2. **Всё грузим как текст** через `COPY` во временные staging-таблицы (`staging.sql`). Это самый быстрый способ залить миллион строк в Postgres, и он не падает на грязных значениях.
3. **Очистка в SQL** (`load.sql`, функция `pg_temp.clean_text`): схлопываем пробелы, обрезаем края, пустую строку превращаем в NULL. После этого приводим типы (`::int`, `::date`, `::float`, `::boolean`).
4. **Дедупликация.** Лот берём один (`DISTINCT ON (lot_id)`, самая свежая публикация). Заявку берём одну на пару (лот, ИНН), победа через `bool_or`.
5. **Валидация ИНН**: только 10 или 12 цифр (`^\d{10}(\d{2})?$`). КПП поставщика берём самый частый.
6. **Площадка**: `is_eshop_or_aisgz = 'ЭМ'` превращаем в `true`.
7. **Метка набора `dataset`**: `history` для истории с заявками, иначе имя пакета. Так в одной таблице живут история и загруженные пакеты будущих закупок.
8. Режимы: `--replace` (TRUNCATE и полная перезагрузка) и `--append` (дозагрузка без потери истории).

## 3. Как работает поиск (онлайн, `api/recommend.py`)

### 3.1 Вход

`POST /match/search`:
- **Категория ОКПД2** не короче `XX.XX`. Слишком общий код (`32`) отклоняем, потому что разные товары смешались бы в одну кучу. Можно указать уточнённый код (`32.50.13`), тогда похожие лоты фильтруются по префиксу.
- **НМЦК** (обязательно, > 0).
- **Площадка**: АИС ГЗ / ЭМ / все.
- **Только МСП**.
- **ИНН заказчика** (необязательно): включает признаки «уже работал с этим заказчиком».

Автодополнение категорий (`api/categories.py`) показывает только коды, которые реально встречаются в данных. Сначала идут совпадения по коду, потом по названию; без запроса показываем самые популярные группы.

### 3.2 Шаги

**Шаг 1. Похожие лоты.** Берём все лоты, где есть товар из той же группы `XX.XX` и код начинается с выбранного префикса (`SIMILAR_LOTS_SQL`). Для каждого считаем число участников. Для пакетного лота берём все группы его товаров (`extra_codes`).

**Шаг 2. Профиль каждого поставщика на похожих лотах** (`HISTORY_SQL`, один SQL-запрос):
- `part`: всего заявок, `wins`: побед;
- `comp_part` / `comp_wins`: заявки и победы **в конкурентных** лотах (≥2 участников);
- `direct_cnt`: лоты, где он был единственным участником;
- `last_date`: последняя заявка;
- `eshop_bids`: сколько заявок в ЭМ;
- `typical_price`: медианная НМЦК его лотов;
- `customer_group_bids`: заявки этому заказчику в этой категории;
- `lot_ids`: по ним берём текстовую «типичность» (см. 4.4).

Ликвидированных и банкротов (по данным DaData) исключаем сразу.

**Шаг 3. Отбор кандидатов** (`select_candidates`). Тот же отбор, что и при обучении:
- топ-50 по победам;
- топ-50 по свежести последней заявки;
- все, кто уже подавал заявки этому заказчику в этой категории.

Зачем два списка: по победам находим сильных, по свежести находим активных сейчас, в том числе новичков, у которых ещё мало побед.

**Шаг 4. Фильтр МСП.** Если стоит «только МСП», оставляем поставщиков, которые хоть раз участвовали в закупке «только для СМП». Это косвенный признак (см. «Слабые места»).

**Шаг 5. Признаки и скоринг моделью.** Для каждого кандидата считаем 23 признака (раздел 4.3), LightGBM выдаёт «сырой» балл ранжирования. Если площадка «все», считаем балл для обоих вариантов и берём лучший.

**Шаг 6. Калибровка.** Сырой балл ранжирования сам по себе бессмыслен: это не вероятность и не сравнивается между запросами. Вторая маленькая модель переводит его в **вероятность, что поставщик подаст заявку** (раздел 4.6).

**Шаг 7. Итоговая «подходимость» 0–100.** Это рабочая версия в `recommend.py`, ещё не закоммичена:
- ожидаемая ценность = P(подаст заявку) × сглаженная доля побед в конкурентных закупках `(comp_wins + 1) / (comp_part + 5)` (байесовское сглаживание с априорной долей 20%: у новичка с 1/1 нет 100%);
- переводим в 0–100 по **логарифмической** шкале (от 0,1% до потолка). Вероятности различаются на порядки, в линейной шкале все кроме первых слились бы в ноль;
- `lift`: во сколько раз выше среднего кандидата. В интерфейсе это фраза «подают заявки в N раз чаще среднего кандидата».

> В последнем коммите формула проще: подходимость = лог-шкала от P(участия) от 0,5% до 70%. Перед защитой сверьте, какая версия будет на демо.

**Шаг 8. Диверсификация.** Всего 30 мест: первые 25 строго по скору, затем до 5 мест для **«претендентов»** из хвоста. Претендент: ≥3 конкурентных заявок, побед < 20%, вероятность участия ≥ 10%. Зачем: это компании, которые уже следят за категорией и готовы подаваться. Их приглашение напрямую повышает конкуренцию, а модель, которая учится предсказывать победителя, сама их вниз задвигает.

**Шаг 9. Новые поставщики** (`NEW_SQL`). Добавляем в конец выдачи компании из обогащения (`source = dadata/web`), у которых код категории совпадает с запросом (по префиксу в обе стороны). Скор у них отдельный, эвристический, из 100 баллов:

| Сигнал | Баллы |
|---|---|
| Совпадение кода категории (полное / частичное) | 30 / пропорционально |
| Основной ОКВЭД совпадает по первым 2 цифрам | 10 |
| Роль: производитель / дистрибьютор / поставщик | 20 / 15 / 10 |
| Статус «действующая» / неизвестен | 10 / 5 |
| Возраст компании (полный балл с 3 лет) | до 10 |
| СПб или ЛО | 10 |
| Есть сайт | 5 |
| Есть контакты | 5 |

В интерфейсе вместо оценки для них пишем «нет истории закупок». Мы честно не смешиваем эту шкалу со шкалой модели.

**Шаг 10. Обогащение выдачи.** Для каждого добавляем последние 5 похожих лотов (предмет, НМЦК, заказчик, победил или нет). Если названия нет, в фоне запрашиваем его в ЕГРЮЛ, и при следующем открытии оно уже подставлено.

**Фолбэк без модели.** Если файлов модели нет, используется ручная формула (`formula_score`): 25 баллов за опыт (лог), 25 за сглаженную долю побед, 20 за свежесть (линейно за 2 года), 10 за местного, 10 за площадку, 10 за попадание в ценовой диапазон. Скор нормируется min-max и называется «Релевантность». Это гарантия работоспособности: сервис не падает, даже если ML-часть не собрана.

## 4. Модель: как и зачем обучали (`ml/`)

### 4.1 Постановка

**Что хотели узнать:** кто из известных поставщиков **подаст заявку и выиграет** на новом лоте.

**Почему ранжирование, а не классификация.** Заказчику нужен упорядоченный список: кого звать первым. Поэтому это задача **learning-to-rank**. Запрос = лот, документы = кандидаты-поставщики.

**Метка (relevance):** `participated + won`:
- 2: победил;
- 1: подал заявку, но не выиграл;
- 0: кандидат, который не пришёл.

**Целевая функция:** `lambdarank` в LightGBM. Она напрямую оптимизирует NDCG, то есть порядок наверху списка.

### 4.2 Защита от утечки: временной сплит

Признаки считаются **только по истории до даты отсечки**. Метки берутся **из следующего квартала**. Это ровно то, что произойдёт в жизни: прошлое известно, будущее нет.

| Набор | История для признаков | Лоты-цели |
|---|---|---|
| Обучение (для оценки) | до 30.06.2025 | III кв. 2025 (июль–сентябрь) |
| Тест | до 30.09.2025 | IV кв. 2025 (октябрь–декабрь) |
| Калибровка | до 30.06.2025 | III кв. 2025, половина лотов |

- Берём **только конкурентные лоты** (≥2 участников), почему см. 1.3. Если лотов больше 30 000, сэмплируем (seed фиксирован).
- Кандидаты генерируются **тем же правилом, что и в проде** (топ-50 по победам + топ-50 по свежести + история с заказчиком). Поэтому метрики честно отражают поведение сервиса.
- **Итоговая модель** после оценки переобучается на самом свежем квартале (IV кв.): в проде важнее актуальность. Метрики в отчёте посчитаны моделью, которая тест не видела.

### 4.3 Признаки (23 штуки)

| Группа (как в объяснении) | Признаки | Смысл |
|---|---|---|
| Опыт в конкуренции | `comp_part`, `comp_wins`, `comp_win_share` | Сколько раз подавался туда, где были соперники, и как часто выигрывал |
| Объём в категории | `part`, `wins`, `win_share` | Общий опыт в группе ОКПД2 |
| Без конкурентов | `direct_cnt`, `direct_share` | Как часто был единственным участником |
| Профиль | `total_bids`, `groups_cnt`, `class_bids`, `spec_share` | Узкий специалист или «всеядный»: сколько всего заявок, во скольких группах, сколько в классе XX, доля категории в его работе |
| Типичность | `typicality` | Типичны ли для категории предметы его лотов (текстовый признак, см. 4.4) |
| Активность | `days_since_last` | Дней с последней заявки в категории |
| Цена | `price_fit` | Насколько НМЦК близка к его обычной: `1 − |log10(НМЦК / медиана)| / 2`. Разница в 10 раз даёт 0,5, в 100 раз даёт 0 |
| Площадка | `platform_share` | Доля его заявок на нужной площадке |
| Заказчик | `customer_bids`, `customer_group_bids` | Заявки этому заказчику: всего и в этой категории |
| Регион | `is_local` | СПб (78) или ЛО (47). Регион по КПП, иначе по первым цифрам ИНН |
| МСП | `is_msp` | Участвовал в закупках только для СМП |
| Контекст лота | `lot_log_price`, `lot_is_eshop`, `lot_is_smp` | Одинаковы для всех кандидатов лота. Нужны только для взаимодействий, в объяснения не попадают |

### 4.4 Текстовая «типичность» (`ml/text.py`)

**Проблема:** в одной группе ОКПД2 бывают «неродные» лоты (например, работы закодированы как товар). Поставщик, который выигрывает только такие лоты, не настоящий профильный игрок.

**Решение:**
1. Предмет закупки (`subject`) разбиваем на слова от 3 букв и обрезаем до 6 символов. Это простой стемминг для русского: «картриджей» и «картридж» дают «картри».
2. Строим TF-IDF (`min_df=5`, до 50 000 признаков, сублинейный TF) и нормируем.
3. Для каждой группы ОКПД2 считаем **центроид**: средний вектор её лотов.
4. **Типичность лота** = косинусная близость лота к центроиду своей группы.
5. **Типичность поставщика** = средняя типичность его лотов в категории.

Результат сохраняется в `ml/model/lot_typicality.npz`, API берёт готовые значения бинарным поиском. Метки при этом не используются (обучение без учителя), поэтому утечки целевой переменной нет.

Почему не эмбеддинги и не LLM: по брифу логику рекомендаций на LLM строить нельзя. TF-IDF быстрый, объяснимый и работает офлайн.

### 4.5 Гиперпараметры

```
LGBMRanker(objective="lambdarank", n_estimators=400, learning_rate=0.05,
           num_leaves=63, min_child_samples=50,
           subsample=0.8, subsample_freq=1, colsample_bytree=0.8)
```
Это стандартные устойчивые параметры для бустинга: небольшой шаг, много деревьев, бэггинг по строкам и признакам против переобучения, `min_child_samples=50` против листьев под единичные примеры.

### 4.6 Калибровка вероятностей (`ml/calibrate.py`)

**Зачем.** Скор lambdarank имеет смысл только внутри одного лота. Пользователю нужна понятная шкала, одинаковая для всех поисков.

**Как.** Отдельный бинарный LightGBM-классификатор (150 деревьев, 15 листьев, `min_child_samples=500`) на трёх входах:
- `raw`: сырой балл;
- `gap`: отставание от лучшего кандидата в этом лоте;
- `rank`: место в списке.

Цель: **подал ли заявку**. Наложены **монотонные ограничения** (+, +, −): выше балл и ближе к лидеру дают не меньшую вероятность, дальше в списке не большую. Так калибровка не может «перевернуть» порядок. Потолок 70%, чтобы не обещать гарантий.

Учим на половине лотов III кв. 2025, проверяем на другой половине (8 523 лота). Итоговая модель эти лоты не видела.

**Насколько честны вероятности (reliability):**

| Обещали | Средний прогноз | Реально подали | Строк |
|---|---|---|---|
| 0–10% | 1,5% | 1,4% | 661 660 |
| 10–20% | 14,1% | 13,8% | 33 593 |
| 20–30% | 24,2% | 23,1% | 13 825 |
| 30–40% | 34,6% | 33,9% | 6 478 |
| 40–50% | 44,3% | 42,9% | 4 540 |
| 50–60% | 55,0% | 52,9% | 1 286 |

Первому в списке обещаем в среднем 40,4%, реально подают **39,5%**. Базовая доля участия случайного кандидата **3,07%**, то есть первый в нашем списке приходит в 13 раз чаще случайного.

### 4.7 Метрики качества (тест: IV квартал 2025)

| Метрика | Топ по победам (бейзлайн) | Ручная формула | **LightGBM** |
|---|---|---|---|
| Победитель в топ-10 | 31,4% | 26,2% | **53,5%** |
| Доля реальных участников в топ-10 | 27,5% | 17,9% | **46,9%** |
| MRR победителя | 0,152 | 0,124 | **0,309** |
| Медианная позиция победителя | 14 | 17 | **4** |
| Победитель среди кандидатов (потолок recall) | 71,3% | 71,3% | 71,3% |

Как это рассказывать:
- **Winner in top-10 (HitRate@10)**: в скольких лотах победитель оказался в первой десятке.
- **Participants found (Recall@10)**: какая доля реальных участников лота попала в десятку. Это важно для задачи «кого позвать».
- **MRR**: среднее 1/позиция победителя. 0,31 значит, что в среднем победитель примерно на 3-й позиции (с учётом промахов).
- **Потолок 71,3%**: в 29% лотов победитель вообще не попал в кандидаты. Он новичок в категории или вне топ-100. Это ограничение генератора кандидатов, а не ранкера. Доля взятого от потолка: 53,5 / 71,3 ≈ **75%**.
- Ручная формула хуже бейзлайна. Это аргумент, **почему понадобилась модель**: интуитивные веса не работают, а данные сами показали, что важно.

### 4.8 Что модель считает важным (gain, итоговая модель)

| Признак | Доля важности |
|---|---|
| `customer_bids`: заявки этому заказчику | **32,6%** |
| `comp_part`: опыт в конкурентных закупках | **16,6%** |
| `customer_group_bids`: заказчик + категория | 9,0% |
| `price_fit`: попадание в ценовой диапазон | 5,5% |
| `days_since_last`: свежесть | 4,3% |
| `comp_win_share` | 3,8% |
| `total_bids`, `class_bids`, `groups_cnt`, `typicality` | ≈3% каждый |
| `win_share`, `spec_share`, `comp_wins`, `part` | 2–3% |
| `platform_share`, `direct_*`, `wins` | 1–1,5% |
| `is_msp`, `is_local` | ≈0 |
| `lot_is_eshop`, `lot_is_smp` | 0 (константа внутри лота) |

**Бизнес-выводы:**
1. **Самый сильный сигнал: связка «поставщик–заказчик».** У заказчиков есть «свои» поставщики. Поэтому поле «ИНН заказчика» в форме сильно улучшает подбор. Для развития конкуренции это же и предупреждение: без подсказки система будет звать «своих», поэтому отдельно выводим претендентов и новых.
2. **Опыт именно в конкурентных закупках** важнее общего объёма и побед без соперников.
3. Масштаб цены и свежесть активности: поставщик лотов на 50 тыс. ₽ вряд ли придёт на лот в 50 млн ₽.
4. `is_local` ≈ 0: почти все участники и так местные, признак не различает.

### 4.9 Ретро-кейсы (`python -m ml.cases`)

Скрипт берёт случайные реальные лоты IV кв. 2025 и печатает: предмет, НМЦК, площадку, наш топ-5 с пометками 🏆 победил / ✅ участвовал, на каком месте реальный победитель, сколько реальных участников попало в топ-10. Удобно показать жюри «живьём». **Перед защитой прогоните и выпишите 2–3 удачных и 1 неудачный кейс с объяснением.**

### 4.10 Объяснимость

Для каждого кандидата считаем **вклад каждого признака** в балл модели: `predict(pred_contrib=True)` в LightGBM, это TreeSHAP. Вклады складываем в 11 понятных групп (`FACTOR_GROUPS`), сортируем по модулю и превращаем в человеческий текст (`group_text`):
- плюс: «Уже работал с этим заказчиком: 12 заявок, в этой категории 5»;
- минус: «Обычно участвует в лотах около 40 тыс. ₽, далеко от вашей НМЦК».

В карточке: до 3 причин «Почему рекомендуем» и до 5 факторов со знаком и силой влияния. Отдельные бейджи: «Претендент», «💤 давно не участвовал, стоит напомнить», МСП, ИП, филиал (КПП[4:6] = 43), «ликвидируется».

Объяснение **честное**: это разложение того самого балла, по которому отсортирован список, а не отдельно придуманный текст.

## 5. Обогащение: откуда данные и что с ними делаем

Цель обогащения: (1) вместо голых ИНН показать проверенные карточки компаний, (2) **найти новых поставщиков**, которых нет в истории госзакупок, (3) определить роль (производитель / дистрибьютор / поставщик).

### 5.1 Источник 1. ЕГРЮЛ ФНС (`worker/egrul.py`): названия и проверка существующих

- Открытый сервис `egrul.nalog.ru`: POST с ИНН, получаем токен, затем `search-result/{token}`, ответ JSON.
- Берём: **название, ОГРН, КПП, регион, дату прекращения деятельности**.
- Когда вызывается: после каждого поиска, в фоне (`BackgroundTasks`), для поставщиков из выдачи без названия. Не больше 30 за поиск и 300 за пакет, чтобы не долбить сервис.
- Кеш: `worker/.cache/egrul/{inn}.json`. Повторно не запрашиваем.
- В интерфейсе бейдж «Название получено из открытых данных ФНС».

### 5.2 Источник 2. DaData (`worker/dadata.py`, `api/enrichment.py`): главный канал новых поставщиков

DaData отдаёт данные ЕГРЮЛ/ЕГРИП через API с фильтрами.

**Как ищем новых для категории:**
1. Запрос `suggest/party` с фильтрами:
   - `okved = [группа ОКПД2]`: **ключевая идея**. ОКПД2 (продукция) и ОКВЭД2 (виды деятельности) построены на одной европейской основе (КПЕС / NACE), поэтому первые уровни кодов совпадают. Товар 31.01 «мебель для офисов» соответствует деятельности 31.01 «производство мебели для офисов»;
   - `status = ACTIVE`: только действующие;
   - `branch_type = MAIN`: только головные организации, без филиалов;
   - `locations = kladr 78, 47`: только СПб и ЛО.
2. Suggest требует текстовый запрос и отдаёт до 20 компаний. Поэтому перебираем нейтральные запросы (`ООО`, `Санкт-Петербург`, `Ленинградская`, `ИП`, `АО`, `проспект`, `улица`, …): каждый даёт новый срез компаний.
3. Отсекаем тех, кто уже есть в базе (по ИНН).
4. Парсим ответ (`parse_party`): название с ОПФ, КПП, ОГРН, статус, даты регистрации и ликвидации, основной ОКВЭД, адрес, регион (по КЛАДР), ОПФ, ИП или ЮЛ, численность. Полный JSON ответа тоже сохраняем (`suppliers.dadata`), это происхождение данных.
5. **Роль по ОКВЭД** (`role_from_okved`), с причиной, которую видно в интерфейсе:
   - разделы 10–33 (обрабатывающие производства): **производитель**;
   - 46 (оптовая торговля): **дистрибьютор**;
   - остальное: **поставщик**.
6. Записываем в `suppliers` с `source='dadata'`, `okpds=[категория]`, `enriched_at=now()`.

**Режимы (экран «Новые поставщики»):**
- **Одна категория**: до 50 новых, до 10 запросов.
- **Все категории**: проходим группы ОКПД2 по популярности, добираем до 20 новых на категорию (не больше 3 запросов на категорию), уже найденных учитываем.
- Прогресс в реальном времени (запросов сделано, найдено, текущая категория, таблица найденных).

**Надёжность:**
- дневной лимит (по умолчанию 9 500, счётчик в файле), пауза 50 мс между запросами;
- 401/403 (ключ не принят) и 429 (частота) не ломают сервис: задача переходит в статус «остановлено» с понятным сообщением, найденное сохраняется;
- в коде есть и `fetch_party` (проверка по ИНН через `findById` с кешем на 7 дней), но в основном сценарии она сейчас не вызывается.

### 5.3 Источник 3. Открытые сайты (`worker/adapters.py`, `worker/utils.py`): экспериментальный

Архитектура адаптеров: `SiteAdapter` с методами «найти страницы» и «распарсить страницу». Реализован адаптер zakupki.gov.ru (ЕИС). Разбор страницы:
- **ИНН** регуляркой рядом со словом «ИНН» + **проверка контрольной суммы** ИНН (10 и 12 знаков), чтобы не брать случайные числа;
- **контакты**: e-mail и телефоны (+7/8, нормализация к `7XXXXXXXXXX`), до 3 каждого;
- **роль по тексту сайта**: «собственное производство / производим» значит производитель, «официальный дилер / дистрибьютор / оптовые поставки / собственный склад» значит дистрибьютор;
- **верификация через ЕГРЮЛ**: компания существует, не ликвидирована, регион 78/47. Иначе отбрасываем с причиной;
- кеш страниц, пауза 0,5 с, браузерный User-Agent.

> Честно: этот канал не доведён до основного сценария. Эндпоинт `/enrich` и `api/jobs.find_new_suppliers` вызывают `discover` с несовпадающей сигнатурой. В интерфейсе он отражён только счётчиком «найдено ранее в открытых источниках». На защите подавайте его как «каркас для масштабирования на другие источники», а основной канал это DaData.

### 5.4 Достоверность и происхождение (provenance)

- У каждого поставщика есть `source`: `dataset` (из закупок) / `dadata` / `web`.
- Бейдж в карточке:
  - «Сверено с ФНС через DaData» + дата `enriched_at`;
  - «Название из открытых данных ФНС» (ЕГРЮЛ);
  - «Сведения только из истории закупок, реквизиты не проверялись».
- Ликвидированные и банкроты исключаются из выдачи. «Ликвидируется» и «Реорганизация» показываются флагом.
- Роль всегда с причиной («основной ОКВЭД 46.69 — оптовая торговля»).

## 6. Пакетный подбор (`api/batches.py`)

1. Загружаешь CSV извещений и товаров (заявок нет, это будущие закупки) и даёшь пакету имя. Используется тот же загрузчик, что и для истории. Если все лоты уже были загружены, получаешь ошибку.
2. Запускаешь расчёт: по каждому лоту в 4 потока вызывается тот же `recommend()`. Параметры берутся из самого лота: основная группа ОКПД2 и все группы его товаров, НМЦК, площадка, СМП, заказчик, **дата лота**. Результат пишется в `lot_recommendations` (JSONB).
3. Таблица лотов с топ-3, прогресс, «досчитать только недостающие», «пересчитать один лот».
4. **Экспорт CSV** (UTF-8 с BOM, чтобы открывался в Excel): лот, топ-N поставщиков, скор, роль, новый или из истории, конкурентные заявки и победы, причины.
5. Потом в фоне подтягиваются названия из ЕГРЮЛ для топ-10 каждого лота.

## 7. Архитектура и стек

```
Браузер ──► nginx :80 ──► /        → frontend (React + Vite, собран в nginx)
                      └─► /api/    → api (FastAPI, Python 3.12)
                                          │
                                          ├─► PostgreSQL (история, поставщики, подборы)
                                          ├─► ml/model/* (LightGBM-модели, типичность)
                                          └─► DaData / egrul.nalog.ru (обогащение)
Офлайн: parser/load.py (CSV → Postgres) → ml/train.py (модель, калибровка, метрики)
```

- **Docker Compose**: `db` (postgres, начальный дамп из `.database/dumps`), `adminer`, `api`, `frontend`, `nginx`.
- **API**: FastAPI. Подбор работает на psycopg 3 с «сырым» SQL (агрегации быстрее и прозрачнее). Схема и графики сделаны на SQLAlchemy (async). Модель загружается лениво один раз (потокобезопасно), профили поставщиков кешируются в памяти.
- **Фронт**: React + TypeScript + SCSS-модули. Экраны: Подбор, Пакетный подбор, Новые поставщики, Шорт-лист. Состояние формы, лотов и шорт-листа хранится в localStorage, поэтому переживает перезагрузку. Сейчас добавляется роутинг по URL (`/match`, `/batch`, `/enrichment`, `/shortlist`), пока не закоммичено.
- **Карточка поставщика**: причины, факторы, реквизиты, история участия, графики «Активность за 2 года» (заявки и победы по месяцам) и «Топ категорий ОКПД2» (`/graphs/activity`, `/graphs/okpd`), фильтр по роли.

## 9. Слабые места: что спросят и как отвечать

**«Почему МСП определяете по участию в СМП-закупках, а не по реестру?»**
В данных нет признака МСП у поставщика. Кто подавал заявку в закупку только для СМП, задекларировал статус. Это хороший косвенный признак. Следующий шаг: сверка с Единым реестром МСП ФНС (rmsp.nalog.ru).

**«29% победителей вообще не попадают в кандидатов, это плохо?»**
Это потолок генератора кандидатов: топ-50 по победам + топ-50 по свежести + история с заказчиком. Победитель в этих случаях либо новичок в категории (истории нет вообще, его нельзя предсказать по истории, и для этого у нас есть блок новых поставщиков), либо редкий участник вне топ-100. Расширение пула кандидатов (смежные категории, похожие поставщики) остаётся следующим шагом.

**«Как вы проверили, что нет утечки?»**
Строгий временной сплит: признаки только по прошлому до отсечки, метки только из следующего квартала. Тестовый квартал модель-оценщик не видела. Калибровка проверялась на лотах, которых нет в обучении итоговой модели. Единственное, что считается по всем данным, это TF-IDF-центроиды для типичности: они без меток, только текст, на целевую переменную не влияют.

**«Почему итоговая модель обучена на тестовом квартале?»**
Стандартная практика: сначала честно меряем качество на отложенном квартале, затем для продакшена переобучаем на самых свежих данных, потому что поведение поставщиков меняется. Метрики в отчёте от модели, которая тест не видела.

**«Как скор новых поставщиков сравнивается со скором из истории?»**
Никак, и мы их намеренно не смешиваем: у новых нет истории, на чём обучать вероятность участия, нет. У них отдельная прозрачная эвристика, в интерфейсе «нет истории закупок», в выдаче они идут отдельным блоком после исторических.

**«Насколько точно определяется роль?»**
По основному ОКВЭД: это то, что компания сама заявила в ЕГРЮЛ. Ограничение: многие реально торгуют, имея производственный ОКВЭД, и наоборот. Поэтому причина роли всегда видна пользователю. Для веб-источника роль уточняется по тексту сайта. Честная оценка точности требует ручной разметки выборки. *(Если успели проверить вручную N компаний, назовите цифру.)*

**«Фильтр ОКВЭД = код ОКПД2 не найдёт оптовиков?»**
Да, это ограничение: дистрибьютор мебели имеет ОКВЭД 46.47, а не 31.01. Под фильтр продуктового ОКВЭД попадают в основном производители и сервисные компании. Решение: таблица соответствия «группа ОКПД2 → коды оптовой торговли 46.xx» как дополнительный запрос.

**«Почему вероятность ограничена 70%?»**
Чтобы не обещать гарантий. В калибровочных данных выше ~60% почти нет наблюдений, экстраполяция там ненадёжна.

**«Почему логарифмическая шкала подходимости?»**
Вероятности участия различаются на порядки (от 0,5% до 50%). В линейной шкале все кроме первых трёх получили бы 0–5 баллов. Логарифм лучше передаёт «во сколько раз» один поставщик перспективнее другого.

**«Масштабирование?»**
- Тяжёлое (обучение, типичность) считается офлайн. Онлайн это один SQL с агрегацией по похожим лотам и предсказание бустинга на ~100 кандидатах: быстро.
- Сейчас фоновые задачи и результаты поиска хранятся в памяти процесса (`_results`, `_jobs`). Для нескольких инстансов их нужно вынести в Redis и очередь (Celery / RQ).
- Пакетный расчёт уже параллелится (пул потоков), результаты в БД.
- Нет авторизации и CORS открыт: это прототип.

**«Почему Postgres, а не что-то аналитическое?»**
Объём (≈1 млн заявок) спокойно помещается в Postgres. Агрегации с `FILTER`, `percentile_cont`, `mode()` делаются одним запросом. Плюс одна БД для истории, обогащения и готовых подборов.

**«Почему 71% лотов с одним участником и что это значит?»**
Почти всё это АИС ГЗ: там в данных фактически только победитель. В ЭМ реальная конкуренция (в среднем 2,7 участника). Это и есть боль заказчика, которую решает сервис: показать, кого ещё позвать.
